システムと認証設定を一緒に確認しましょう。 各セクションでは、変更範囲、秘密の処理、障害の挙動について説明します。

## システムおよび製品設定 [#system-settings]

<Callout type="info" title="管理者の運用">

**設定 → システム設定**開け。 明示的にサポートされている製品構成のみが書き写可能であり、インフラの秘密は引き続きデプロイメント管理されます。

</Callout>

### 製品設定 [#system-settings-product-settings]

現在のページでは、商品表示名やデフォルト言語などの非機密設定が公開されることがあります。 保存された更新は共有リビジョンを使用し、サービス再開なしで有効となります。

パーマネント監査はアクターの記録、キー設定、前後の値、メタデータの要求を行います。

### 読み取り専用展開構成 [#system-settings-read-only-deployment-configuration]

データベース、Redis、MinIO、ドキュメント処理、その他のランタイムパラメータ、ファイル制限、JWT/HMAC/暗号化キー、トークン期間、保持は制御された`.env`またはデプロイメント構成のままです。

ページは編集済みの設定状態を表示することがありますが、接続文字列、完全な内部エンドポイント、パスワード、鍵、トークン、暗号化資料は表示されません。 モデルチャンネルはモデル設定ページで管理される明示的な例外です。

### タスクの並行処理 [#system-settings-task-concurrency]

**タスクの同時実行数**タブでは、管理者が2つのデプロイメントデフォルトを上書きできます:

- システム全体で動作するタスク制限は、すべてのユーザーでタスクの実行に上限を設けています。
- ユーザーごとのタスクプロセス制限は、各ユーザーワーカーがロードするCodexアプリサーバーのプロセスに上限を設けています。

どちらかのフィールドを空欄にすると、対応する展開のデフォルトが維持されます。 新しいタスクが起動し、サービス再起動なしで最新の保存設定を読み取ることができます。 制限を下げても実行中のタスクは中断されません。新しいタスクやプロセスの承認は、現在の使用が新しい制限を下回るまで一時停止されます。

### システムアップデート [#system-settings-system-update]

**システム更新**は公式のGitHubリリースをチェックし、安全なアップグレードワークフローを表示する別の管理者ページです。 ウェブページは展開を静かにアップグレードしません。 準備、ホストコマンド、アップグレード後の検証については[LinkSenseのアップデートを確認しインストールしてください](./operations.mdx#system-update)を参照してください。

### 定期メンテナンス [#system-settings-scheduled-maintenance]

**システムメンテナンス**タブを開き、理由と開始・終了時刻を入力し、スケジュールメンテナンスを有効にしてください。 メンテナンスは、現在の時間が設定されたウィンドウに入り、指定された終了時に自動的に終了したときにのみ有効になります。

メンテナンス終了時、システムは自動的にスケジュールメンテナンスをオフにし、理由、開始時刻、終了時間、期間をクリアします。 追加のセーブは不要で、管理者が設定ページを開いていてもクリーンアップが実行されます。 開いた設定ページは数秒で更新されます。 サービス停止中に終了したメンテナンスは、サービス再開時にクリアされます。

アクティブなメンテナンス中、サインインした管理者はサインインおよびメンテナンス設定以外のページで**システムメンテナンス中**ダイアログを表示します。 このブラウザのアカウントの現在のメンテナンス期間中は、**今後表示しない**を選択してください。 選択はナビゲーション、リフレッシュ、再開を経て、タブ間で同期されます。 メンテナンスの詳細を編集したり、現在の期間を延長しても再び表示されません。新しい生理が始まるとそうです。 他のアカウントやデバイスは影響を受けていません。 設定ページを直接開くには**メンテナンス設定**を選択してください。 リマインダーはそのページに隠れたまま、リフレッシュや繰り返しのナビゲーション後も含まれます。 閉じボタンとEscは現在のページのリマインダーだけを無効にします。別のページに移動してもまた表示されます。 メンテナンス終了または無効化されるとダイアログは消え、サインインやメンテナンス設定のページには表示されません。 サインインした管理者ページの右下にも**システムメンテナンス中**リンクが残り、メンテナンス設定を開きます。 ダイアログを閉じたり抑制したりしても、このインジケーターは隠されません。メンテナンスが終わると消えます。

メンテナンス中:

- 一般ユーザーは専用ページで理由や期待されるメンテナンスウィンドウを確認でき、ビジネスAPIを呼び出すことはできません。
- 管理者は依然としてサインインし、システムを使って状況の確認、スケジュールの調整、またはメンテナンスの早期終了が可能です。
- サインイン、初期化、健康状態、現在ユーザーIDは引き続き利用可能で、管理者がロックアウトされることはありません。

保存前にデバイスのタイムゾーンを確認し、現実的な終了時間を提示してください。

### 対立と失敗 [#system-settings-conflict-and-failure]

修正チェックは、ある管理者が他の管理者を静かに上書きすることを防いでいます。 コンフリクトではリフレッシュし、最新の状態を確認し、再度変更を確認します。

サーバーは、カスタムリクエストがUIをバイパスしても、デプロイ専用設定の変更を拒否します。

### 推奨事項 [#system-settings-recommendations]

- リスクの低い期間中に組織全体の表示設定を変更しましょう。
- 通常のユーザーアカウントで結果を検証してください。
- ログイン機能の変更は別々の認証セクションを使ってください。

## 認証、メールおよびサインイン方法 [#authentication-settings]

<Callout type="info" title="管理者の運用">

**設定 → システム設定**では、メール配信には**認証メール**、企業やサードパーティアカウントには**ログイン方法**を使いましょう。 各構成は独立してセーブされます。

</Callout>

### 構成モード [#authentication-settings-configuration-modes]

認証メール、エンタープライズSSO(OIDC)、Teamsサポート内のサインイン機能:

- **デプロイ環境を継承**;
- 暗号化ストレージを**システム設定で管理**;
- **無効**、環境のバックアップもありません。

マネージドモードから切り替えたり、設定済み認証を無効にするには確認が必要です。

### 認証メール [#authentication-settings-authentication-email]

SMTPホスト、ポート、STARTTLSまたは直接TLS、送信者、オプションのユーザー名、パスワードを設定しましょう。 空のユーザー名はSMTPパスワード認証がないことを意味します。 このサービスはファーストパスワードとリセットのメールを送信します。システムヘルスでその接続を確認してください。

### オープン登録 [#authentication-settings-open-registration]

**第三者アカウント→サインイン方法**でオープン登録を有効にしてください。 自己登録ユーザーは、管理者が作成またはインポートしたユーザーと、[割当管理](./models-and-usage.mdx#quota-settings)メンバーの週間クォータ基準を共有します。

オープン登録を無効にすると新規リクエストがブロックされ、発行されたがまだ使用されていないアクティベーションリンクが無効になります。 管理者が直接作成したアカウント、既に有効化されたアカウント、またはその他の設定されたサインイン方法を削除しません。

### エンタープライズアカウント [#authentication-settings-enterprise-accounts]

組織管理アカウントを使いましょう。 新規アカウントは登録設定に関わらず管理者のアクティベートが必要です。

#### エンタープライズSSO(OIDC) [#authentication-settings-enterprise-sso-oidc]

HTTPS発行者のURL、クライアントID、クライアントシークレットを入力します。 LinkSenseは読み取り専用のコールバックURLを派生し表示し、プロバイダーにも登録する必要があります。

新しいリビジョンは、古いリビジョンで始まった未完了のコールバックを無効にします。 ユーザーはサインインを再開する必要があります。 初回SSO識別は、メールで保留中のアカウントを作成します。管理者はユーザーが再びサインインする前にこれを有効にしなければなりません。

#### エンタープライズSSO(SAML 2.0) [#authentication-settings-enterprise-sso-saml-20]

サイトでHTTPSを設定し、アイデンティティプロバイダーのエンティティID、サインインURL、PEM署名証明書を入力します。 表示されているサービスプロバイダーエンティティIDとACSコールバックURLをプロバイダーに登録するか、保存してSAMLを有効にしてXMLメタデータのダウンロードとインポートを行ってください。

提供者は声明に署名し、正確で組織管理のメールアドレスを提供しなければなりません。 メールの属性名と正確に一致してください。メールアドレスとしてその識別子を使うには`NameID`を入力してください。 名前属性は任意です。 既存のアカウントはメールでマッチングされ、役割は保持されます。 新規アカウントは管理者の有効化が必要です。無効なアカウントはサインインできません。

プロバイダーが署名済み認証要求を必要とする場合は、リクエスト署名を有効にし、サービスプロバイダーのRSA証明書とそれに対応する秘密鍵を入力します。 保存された鍵は決して返却されません。他のフィールドを変更するときは秘密鍵を空欄のままにしてください。 リクエスト署名を無効にして保存すると、その証明書とキーは削除されます。 期限切れのアイデンティティプロバイダー証明書を置き換えてサインインを復元します。

メンバーはLinkSenseのサインインページで**SAMLエンタープライズアカウントでサインイン**から始めます。 各フローを5分以内に完了してください。設定変更後に再起動してください。 このバージョンは、IdPによるサインイン、暗号化アサーション、単一ログアウトなし、SPによるサインインのみをサポートします。 LinkSenseからのサインアウトは、アイデンティティプロバイダーからのサインアウトではありません。

#### Teams内でサインイン [#authentication-settings-sign-in-within-teams]

ここでMicrosoft EntraのテナントIDとクライアントIDが登場します。 LinkSenseの設定はEntraの登録、Application ID URI、Teamsのマニフェスト、管理者の同意を置き換えるものではありません。

### サードパーティアカウント [#authentication-settings-third-party-accounts]

Google、Apple、Microsoftの個人アカウント、Facebook、GitHubを設定しましょう。 Microsoftの職場や学校のアカウントでは、エンタープライズアカウントの下にMicrosoft Entra IDを設定してください。

GitHubでは、開発者設定でOAuthアプリを作成し、設定ダイアログからコールバックアドレスをAuthorizationコールバックURLにコピーします。 LinkSenseでクライアントIDとクライアントシークレットを入力して有効にします。 テスト環境と本番環境ごとに異なるコールバックURLを持つ別々のアプリを作成しましょう。 サインインはメールアクセスのみを要求し、リポジトリへのアクセスは要求しません。 GitHubが認証済みのメールアドレスを提供できない場合、新規ユーザーはLinkSenseを通じてメール認証をしなければなりません。

登録が開かれている間は、新規ユーザーは管理者のアクティベートなしでメール認証後に開始できます。 既存ユーザーはまずサインインし、アカウントを**セキュリティ→設定 →連携したサードパーティアカウント**で連携する必要があります。一致するメールは自動的にマージされません。 登録を終了しても、連携したアカウントのサインインはブロックされません。

### 秘密の取り扱い [#authentication-settings-secret-handling]

APIは設定済みフラグのみを返し、SMTPパスワードやOIDCシークレットは一切返しません。 管理モードでは、変更しない秘密を空欄にしておく;別のモードから切り替えるには、再度そのモードに入る必要があります。

破損または復号不可能な設定は閉じられず、未確認の古い値に戻ることはありません。
